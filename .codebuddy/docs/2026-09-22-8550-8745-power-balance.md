## [warn] 一个必须先讲清楚的前提：采集态本身在耗电

`logd` 在 8745 待机占 **17.44 %**、launcher 占 **15.82 %**、游戏占 9 %；8745 待机 5 小时产出 **16.7 MB** devimp（≈0.9 KB/s）。

**dev_record 开着时，日志系统自己是实打实的负载**（logd 单线程打满一个小核 ≈ 上面那个「小核 util 71 %」）。
所以：日志里的功耗与负载读数**包含了采集自身的开销**，真实日常会更低；评估任何改动的效果，必须**前后都在同样的 dev_record 状态下**比（都开或都关），否则会得出假结论。

## [plan] 改进方案（按「先纯配置、后代码」排，兼顾三者）

### P1 — 日常 CLG 加天花板（空间最大，先做）

`module/config/8550/feature.yaml` + 通用配置里 `default.cpu_load_governor`：

```yaml
default:
  cpu_load_governor:
    perf_ceil: 0.80        # 原 1.0（无天花板）
    touch_boost_ms: 400    # 350 -> 400，稳态降频但交互跟手靠它兜
```

- **流畅度怎么保**：稳态降频 + **`touch_boost` 保留并略延长** —— 触摸时立即升频到 ceil 之上（touch boost 是独立通路），
  交互瞬间不受影响，松手回到低天花板。这是「稳态省电、交互跟手」的标准组合，别只降 ceil 不动 boost。
- 预期：日常 cap p95 从 100 % → 80 %，功耗降 0.3~0.6 W（参照视频那次 1/4 的量级）

### P2 — CLG 也加 per-cluster（代码，做完 P1 再看要不要）

CLG 的 `CpuLoadGovernorConfig` **已有 `perf_ceil`，但是全局一份**，三簇共用；
tuned 那边 9-21 已经加了 `per_cluster` 覆盖（little/prime 单独压）。建议给 CLG 补同样的机制：

```yaml
default:
  cpu_load_governor:
    perf_ceil: 0.85
    per_cluster: { little: { perf_ceil: 0.70 }, prime: { perf_ceil: 0.65 } }
```

理由同视频：三簇形态不同（little 过载、prime 空转），一刀切必然顾此失彼。

### P3 — 8745 游戏 akmode：压顶 + 轻微平滑

```yaml
akmode:
  headroom: 1.15
  perf_ceil: 0.95          # 新增：不再让尖峰顶到 100 %
  util_smoothing: 0.85     # 1.0 -> 0.85，只滤最陡的尖峰，响应几乎不受影响
```

- 目标：big cap p50 从 100 % → 95 %，功耗降 0.5~1.0 W
- **一票否决**：掉帧或操作变粘就回退（`util_smoothing` 先回 1.0，再回 `perf_ceil` 1.0）

### P4 — 8550 游戏：把陡峭的 70 % 限频改平缓

`soft_perf_cap 0.70` 是一刀切。建议 0.70 → **0.85**，并把 `batt_soft_temp_c 41` 之后加一段斜率
（或提高 `free_above` 让中高负载不被误压）。**别直接改安全阈值**——目标是「不要断崖式掉帧」，
真正的解法还是 P1/P3 把功耗压下去让温度不上来。

### P5 — 采集开销（只在长期开 dev_record 时才需要）

- `tgtop` 现在 30 s 一轮全系统扫 /proc，**是 logd 之外最贵的采集动作** → 建议 30 s → 60 s，或做成可配
- snap 1 s 保留（功耗关联锚点，动它会失去分析能力）
- 若要做：新增 `devimp_tgtop_interval_secs` 配置项，默认 60

### P6 — 数据侧补一个坑

devimp **加 `charge` 列**（现在只能靠 `batt_i` 符号猜充放电，这次分析全程踩这个坑）；
同时把 48 列版本刷入，下次就能直接看内核实际频率（而不是只看调度器决策值）。

## [verify] 验证方式

每个改动前后，同机型、同场景、同 dev_record 状态、同亮度/音量/网络，各录 ≥10 分钟：

1. `batt_p` avg / p50（主指标）
2. `cap%` 是否还在 70 %（8550 游戏）以及是否不再触发限频
3. tick 的 `cap%` 三簇是否按预期下移、**util 是否基本不变**（变了说明伤到负载本身）
4. 主观 + fps（若后续 FAS 采样可用）：**掉帧 / 变粘即回退**
5. 日常场景额外看 `logd` 占比是否随 P5 下降

判定：功耗降 ≥0.2 W 且无感知退化 → 采纳；否则回退上一档。

## [done] P1~P4 已落地（2026-09-22，按「全局受益改全局、SoC 差异分 SoC」实施）

| 项 | 改动 | 范围 | 理由 |
|---|---|---|---|
| **P1** | `default.cpu_load_governor.perf_ceil` **1.0 → 0.80** | **全局**：根 `feature.yaml` + 三个 SoC 覆盖文件同步 | 日常档过剩是通病（8550/8745 同向）。**SoC 文件是覆盖层，只改根不生效**，故 `8550 / 8475 / 8998` 三处一起改；8745 无专属目录 → 自动继承根 |
| **P2** | CLG 新增 `per_cluster` 覆盖（代码） | 能力是全局的，**配置只给 8550**：`little 0.70`、`prime 0.65`（big 不覆盖、继承 0.80） | 只有 8550 有实测数据支撑（util little 0.55 / big 0.36 / prime 0.32）；8475 / 8998 **不写**覆盖——没数据就不拍脑袋 |
| **P3** | `akmode`：`perf_ceil 0.95` + `util_smoothing 0.85`（原默认 1.0 / 1.0） | **全局** `normal/tuned_profiles.yaml` | 游戏场景各 SoC 同向受益（8745 实测 7.06 W、big cap 中位数 100%） |
| **P4** | `Thermal.soft_perf_cap` **0.70 → 0.85** | **仅 8550** | 只有 8550 实测撞到断崖限频（batt 40.7 ℃）；8475 / 8998 保持 0.70。**安全阈值本身（batt_soft/hard_temp_c）未动** |

**代码改动 2 个文件**：
- `src/chiri/config.rs`：`CpuLoadGovernorConfig` 加 `per_cluster: HashMap<String, ClgClusterOverride>`；
  新增 `ClgClusterOverride`（只覆盖 up/down 阈值、headroom、floor、ceil 五个量，其余沿用模式级）与
  `effective(cluster)`（返回覆盖后的完整配置副本，含同样的 floor/ceil 交叉约束）。
- `src/chiri/cpu_load_governor.rs`：新增 `cluster_name_for_policy()`（cpufreq 的 policy 名就是该簇首个
  CPU id，配合 `chiri_core_ranges()` 判定，**不额外读 sysfs**）；两处 `CoreGroupWorker::spawn` 由
  `self.cfg.clone()` 改为 `self.cfg.effective(Self::cluster_name_for_policy(policy.id))`。
  **Worker 内部代码零改动**——它仍按单一 `self.cfg` 使用，不需要感知覆盖的存在。

**等价性**：不写 `per_cluster` 时 `effective()` 返回自身克隆，行为**逐位等同于改动前**。
`cargo +nightly check -p chiri --target aarch64-linux-android` 通过。

**没动 `touch_boost_ms`**：8550 日常档本来就是 400 ms（正是建议值），无需改。
**再次强调配套关系**：`perf_ceil` 压下去后，交互响应完全依赖 `touch_boost`（`touch_boost_enabled: true`），
后续若有人觉得「不跟手」，正确做法是调 boost 而不是把 ceil 抬回去。

**数据订正**：报告中 `com.trim.app` 这一行按原样保留包名（不做应用名猜测），其 1.85 W 是滤除充电后的放电值。

**验证与回退**（同机型、同场景、同 dev_record 状态，前后各 ≥10 分钟）：
1. 日常：cap p95 是否从 100 % 落到 ~80 %（little ~70 %、prime ~65 %），`batt_p` 降幅，滑动是否跟手
2. 8745 游戏：big cap 中位数是否从 100 % → 95 %，功耗是否从 7.06 W 下降，**掉帧即回退**
   （先回 `util_smoothing` 1.0，再回 `perf_ceil` 1.0）
3. 8550 游戏：是否还出现 70 % 断崖（`cap%` 曲线应更平缓）
4. 三者的 **`util` 都不应明显变化**——变了说明伤到负载本身，不是省电
