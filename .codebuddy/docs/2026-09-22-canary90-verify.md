# Canary90 首批日志验证（devimpbin/8550/logd_0922-020050.tar.gz）

> 样本：0922-00:52 ~ 02:00（约 1.1 小时），52 个 devimp 文件，**48 列**、模块 `Alpha04-Canary90`
> （上一批是 40 列 / Canary88）→ 本批首次能看到 CPU/GPU 的**实际频率**与调速器。
> 场景：桌面、酷安、QQ、小红书、B站、sgame 游戏、kernelsu。

## [ok] P1 / P2 / P4 的参数都精确生效了

日常 `default` 档（走 CLG）的频率**上限** p95，调参前 vs 调参后：

| 场景 | 调参前（C88）little / big / prime | 调参后（C90） | 配置值 |
|---|---|---|---|
| launcher | 100 / 100 / 100 | **72.4 / 82.9 / 69.9** | 0.70 / 0.80 / 0.65 |
| mobileqq | 94.3 / 87.7 / 100 | **72.4 / 82.9 / 69.9** | 同上 |
| coolapk | 100 / 100 / 100 | **72.4 / 82.9 / 69.9** | 同上 |

顶到配置的档位上沿（0.70→72.4%、0.65→69.9%、0.80→82.9%），说明
**`per_cluster` 覆盖确实按簇生效了**——不是只改了全局。

游戏 fas（sgame）：`cap%` 由 **70 → 85**，符合 P4 的 `soft_perf_cap 0.70 → 0.85`；
`cpu_governor` 在该场景是 `performance` 且 `cur = min = max`（FAS 锁频，频率落在 1.34/1.67/1.88 GHz），符合预期。

## [bad] 但功耗全面上升了——而且是采集自己造成的

**同活跃度对比**（两批都只取亮屏 + 放电，按 `gpu_busy` 分档，避免拿后台段比操作段）：

| gpu_busy 档 | 调参前 C88 | 调参后 C90 | 变化 |
|---|---|---|---|
| < 10 | 1.86 W | **3.17 W** | **+70 %** |
| 10 – 30 | 3.53 W | 4.06 W | +15 % |
| ≥ 30 | 4.11 W | 6.15 W | +50 % |
| cpu_temp（gpu<10 档） | 47.5 ℃ | **58.7 ℃** | +11.2 ℃ |

**同场景对比更干净**（B站 playback，只取放电 + `gpu_busy < 12` 的纯播放样本）：

| 批次 | n | P avg/p50 | cpuT | psi | little cap p95 (util) | big cap p95 (util) |
|---|---|---|---|---|---|---|
| 9-20 基线 | 1479 | 2.39 / 2.41 W | 51.9 | 18.2 | 100 (0.63) | 85.8 (0.50) |
| 9-22 00:14（C88） | 937 | **1.76 / 1.52 W** | 45.9 | 18.6 | 66.7 (0.60) | 75.9 (0.49) |
| 9-22 02:00（C90） | 219 | **2.59 / 2.52 W** | 52.8 | 23.2 | 66.7 (0.66) | 75.9 (0.57) |

**关键判据**：C90 与 C88 的 playback **频率上限完全一样**（little p95 66.7、big 75.9），
也就是说该场景的调参没动过，但功耗从 1.76 W 涨到 **2.59 W（+47 %）**，
同时 `util`（0.60→0.66、0.49→0.57）、`psi_cpu`（18.6→23.2）、`cpu_temp`（+6.9 ℃）同步上升。
**调参没变而功耗涨 → 涨的只能是 C90 新加的东西。**

## [cause] 定位：每秒读 GPU 频率节点，等于每秒把 GPU 唤醒一次

C90 相对 C88 新增的就是 devimp 48 列采集（每秒 snap 时读 CPU 3×4 + GPU 节点×4 个 sysfs）。
其中：

- **CPU 的 cpufreq 节点读取是廉价的**（CPU 本来就在跑，读 `scaling_*` 不额外唤醒）。
- **GPU 不同**：读 Adreno 的 `gpuclk` / devfreq 的 `cur_freq` 会触发 GPU 寄存器访问，
  **GPU 必须处于供电/唤醒状态才能应答**。每秒读一次 ≈ 每秒唤醒一次 GPU。
  这正好解释了「`gpu_busy` 只有 5.2 %（计算负载很低）但功耗与温度都上去了」——
  GPU 没在干活，却被反复从低功耗里拽起来。

对照 devimp 的既有设计也能印证：`place/core` 是 8s 一轮、`tgtop` 是 30s 一轮，
**只有 snap 是 1s**——把「读 GPU 硬件状态」这种有副作用的操作挂在 1s 的 snap 上，是这轮的设计失误。

## [fix] 已做的两处修复

1. **GPU 快照默认关闭（`src/chiri/mod.rs`）**（用户拍板：先止血）。新增总开关
   `GPU_SNAPSHOT_ENABLED = false`，关闭期间 GPU 那 4 列恒为 `-`；CPU 仍每秒采（廉价且是功耗分析的主要锚点）。
   开关之下仍保留 `gpu_snapshot_due()` 的 10 s 节流——将来若确需 GPU 频率数据，改回 true 即可，
   打开时是「10 s 一次」而不是「每秒一次」。实现保留在 `chiri/gpu.rs::devfreq_snapshot()`
   （带 `#[allow(dead_code)]`），彻底避免唤醒 GPU 需要另找不触碰 GPU 硬件的读数路径。
2. **GPU 列本身有 bug，一并修（`src/chiri/gpu.rs`）**：
   - **单位**：devfreq 的 `cur_freq` 与 Adreno 的 `gpuclk` 都以 **Hz** 计，直接写进日志出现了
     `gpu_cur_khz = 110352386`（110 GHz）这种荒谬值 → 统一换算成 **kHz**（>10 MHz 的按 Hz 处理）。
   - **目录去重**：`kgsl-3d0` 同时存在于 `/sys/class/devfreq/` 与 `/sys/class/kgsl/`（前者标准 devfreq、
     后者 Adreno 私有），混读导致 `min 680 MHz` 配 `cur 110 MHz` → 改为**按设备名去重、devfreq 优先**。
   - **governor**：只在标准 devfreq 路径读（Adreno 私有目录的同名节点是频率值不是 governor 名），
     且读到纯数字判定为无效写 `-`。

`cargo +nightly check -p chiri --target aarch64-linux-android` 通过。

**CPU 侧 48 列数据看起来是对的**（schedutil / 游戏时 performance 锁频，量级合理），未做改动。
