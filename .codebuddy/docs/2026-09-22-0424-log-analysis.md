## 二、是否该为网易云（最长场景）建场景特调？—— **不建议**

**支持建的**：它是本包最长稳态（4505 放电样本 > B站 1051），P_avg 3.27W 高于视频播放的 2.69W。

**反对建的（决定性）**：

1. **CPU 侧已经贴负载，没有可压空间**：little `cap/util = 63.6/59 ≈ 1.08`、big `53.3/46 ≈ 1.16`
   （B站是 60/62 ≈ 0.97）——特调能压的只有 CPU 频率上限，而它已经在负载附近，
   再压就是压性能而不是压余量。
2. **开销的大头在 CPU 之外**：`gpu_busy 33.9`（B站 8.1，**4 倍**）；tgtop 显示
   `surfaceflinger 27.7% + vendor display composer 15.2% = 42.9%` 全在显示合成，
   CPU 侧的 app 自身只有 25%。**ChiRi 对 GPU/显示合成没有手段**（`gpu.rs` 只能锁最高频）。
3. **历史上它就是被移除的**：`src/chiri/special_tuned.yaml` 第 40 行「已移除的条目」里明确列着
   `com.netease.cloudmusic`，移除理由是实测与 CLG 基线相当、且对跟手性更敏感。
   现在数据没有推翻那条结论——变的只是它变成了最长场景，而不是变得"有可压余量"。

**结论**：要省它的电，正解不是场景特调，而是**给媒体场景加 GPU 上限（旧 V4）**：
GPU 33.9% 且与功耗强相关（前一轮分析 r=0.851），这是唯一能碰到大头的手段；风险是掉帧，必须先测。

## 三、新发现：迁移率异常升高（需排查）

`BpfStats` 是 **2s 一次增量**（`mod.rs:2712`），据此换算：

| | 迁移（/s） | 唤醒（/s） |
|---|---|---|
| 09-20 包（同机型） | ≈278 | ≈486 |
| **本包（0922-0424）** | **≈2800~3700** | **≈6000~21000** |

**高了约一个数量级**。可疑方向：P2 把三簇上限拉开（0.70 / 0.80 / 0.65）后，簇间频率落差变大，
EAS 在"小核不够快、大核又被压"之间来回搬线程；也可能是这一版统计口径/探针有变。
**建议**：临时回退 `per_cluster` 录一段同场景对比，确认是否由 P2 引起（这是唯一的新增变量）。
