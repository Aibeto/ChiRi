## 核实：FAS 用的是帧间隔还是帧生成时间

结论：**帧间隔**（相邻两次 queueBuffer 的 ktime 差），不是单帧生成耗时。

证据链：

- `yumi-ebpf/src/main.rs` 只有 `handle_frame` 一个 uprobe，挂 `libgui.so` 的 `android::Surface::queueBuffer`，事件体只有 `pid + ktime_ns`（`bpf_ktime_get_ns()`），没有帧开始/结束配对点，原理上也算不出单帧 duration
- `src/monitor/fps_monitor.rs` `ProbeState::ingest`：`delta_ns = ktime_ns - last_ktime_ns`，经 `[1ms, 200ms]` 门后入 `frametimes` 与 `pending`，投喂为 `DaemonEvent::FrameUpdate { frame_delta_ns }`
- `src/scheduler/fas/frame_pipeline.rs` `update_frame`：`actual_ms = delta_ns/1e6`，`current_fps = 1e9/delta_ns`，与 `1000/target_fps` 的 budget 比误差喂 PID/EMA；`heavy_frame_threshold_ms`、`fixed_max_frame_ms` 同口径
- `min_frame_ns() = 1e9 / max_gear() / 2`（`controller.rs`），低于此的间隔直接丢弃

顺带：本轮把超限的 `MEMORY.md` 精简重写（去重合并、移除"旧 WebUI 事实/目标技术栈"等冗余段），并把上述 FAS 口径作为长期事实写入。

## 修复：热重载触发后不生效（WebUI 改 loglevel INFO→DEBUG 无效）

根因在 `utils::watch_path`（已删除，替换为 `utils::DirWatcher`）两处缺陷叠加：

1. **每轮重建 inotify**：`Inotify::init → add_watch → read_events_blocking → 返回即 drop`。两轮之间没有任何 watch 在册，这段窗口内到达的事件被内核直接丢弃。
2. **不过滤文件名**：WebUI 保存是「先写 `meta.yaml.webui.tmp` 再 `mv` 覆盖」（`contract/meta.ts::writeMetaFields`），产生 CLOSE_WRITE(tmp) + MOVED_TO(meta.yaml) 两条事件。监听器被前者唤醒 → 读到**覆盖前**的旧内容（INFO），而真正的 MOVED_TO 恰好落在重载执行期间（旧 fd 已关、新 fd 未建）被丢弃 → 改完永远停在旧值。

对照：`monitor/app_detect.rs::watch_config_file`（rules.yaml）早就做了「常驻 inotify + 按名过滤 + 100ms 静默 + 清空积压」，所以规则热重载没这个问题；meta 这条链路漏了。

改动：

- `src/utils.rs`：新增 `DirWatcher { inotify, buffer }`，`new(dir)` 建实例、`wait_change(file_name)` 只认目标文件的 CLOSE_WRITE/MOVED_TO，其它文件事件忽略继续等；命中后 sleep 100ms 再 `read_events` 清空积压（inotify 0.11 的 fd 默认 NONBLOCK，无事件返回 WouldBlock 退出循环）
- `src/chiri/mod.rs`、`src/scheduler/mod.rs`：两个 config_watcher 改为持有 `Option<DirWatcher>`，实例异常/建失败时置 None 并退避 2s 重建；过滤名取 `config_path.file_name()`
- `src/logger.rs`：`update_level` 加 `LOG_LEVEL: AtomicU8` 记录当前等级，**等级变化时改走 info!**（原来只有 debug!，用户在 INFO 下改完看不到任何回执）——这条是复现/自查的关键
- `AGENTS.md`（热重载断链新增第 4 条）、`MEMORY.md`

验证：`cargo +nightly check -p yumi --target aarch64-linux-android` 通过。

未改动 WebUI——写入链路（单次读改写 + tmp+rename）本身没问题，是监听侧丢事件。

## 修复：特定条件下启动调度不打包 devimp/logs 进 logd

根因：`archive_on_startup` 把 `logs/`/`devimp/` rename 成模块根的 `ziped_<ts>`/`ziped_devimp_<ts>`，再交游离线程 `log_archiver` 异步打包。**进程在打包完成前退出（日志门限 `exit(0)`、panic、手动 kill）会连带杀掉该线程**，staging 目录就此留在模块根——它既不在 `logd/` 也不在 `devimp/`，`enforce_dir_limits` 只扫这两个目录所以扫不到，后续启动也不认领；而 `logs/`/`devimp/` 此时是上一轮重建的空目录，下次启动 `*_has_entries` 为假 → 什么都不归档。现象即「特定条件下启动调度不打包」。触发概率随日志量上升（开 DEBUG/devimp 后 128MB 门限重启变频繁，打包未完就被下一次门限 exit 打断）。

第二个隐患：staging 名用秒级 `MMDD-HHmmss`，同秒两次启动或上一轮遗留同名目录时 rename 报 ENOTEMPTY → `is_ok()` 为假 → **本次整个不归档**。

改动（`src/logger.rs`）：

- 新增 `STAGING_PREFIX = "ziped_"`、`unique_path(dir, stem, ext)`、`unique_staging(root, base)`、`collect_staging_dirs(root)`
- `archive_on_startup`：在 rename **之前**扫描遗留 staging 目录（前置扫描才不会把本轮刚建的目录算成遗留），与本次的一并交同一个 archiver 线程打包，**遗留优先**（本轮若再被打断，下次还能回收）；各自沿用自己目录名生成 zip（保留原时间戳）；空目录直接 `remove_dir_all` 不留空 zip
- 两处 rename 改用 `unique_staging`（`-N` 去重），杜绝 ENOTEMPTY 导致整体不归档
- zip 名不再统一用本次 ts，改为 `zip_name_of(staging_dir)`；返回值语义不变（供 main info 打点）

验证：`cargo +nightly check -p yumi --target aarch64-linux-android` 通过。顺带按 rustfmt 收拢了本轮新增的多行链式调用（`cargo fmt --check` 全仓库本就有大量历史 diff，未整体 fmt）。

未做：未让门限 `exit(0)` 等待 archiver（会拖长重启、有挂住风险），靠下次启动回收兜底已足够。

## 新增：短会话（<30s）直接丢弃日志、不打包

需求：上次启动距本次启动不足 30 秒则清空 logs/ 与 devimp/，不打包；时间从 `logs/daemon.log` 第一行读；注意时区。

时区确认（关键）：log4rs 1.4 的 `encode/pattern/mod.rs` 用 `chrono`，文档明确 `{d,...}` **默认本地时间**（只有显式传第二个参数 `utc` 才是 UTC）→ 本项目 pattern `{d(%Y-%m-%d %H:%M:%S)}` 是本地时间，故解析用 `libc::mktime` + `tm_isdst=-1`（不能用 `timegm`，东八区会偏 −8h 使 30s 判定失效）。

改动：

- `src/logger.rs`：新增 `SHORT_SESSION_SECS=30`、`SHORT_SESSION_DISCARDED`（+`pub fn short_session_discarded()`）、`now_epoch_secs`、`parse_log_ts_secs`（`#[cfg(unix)]` 走 mktime，非 unix 返回 None）、`first_log_line_secs`（只读前 256 字节，daemon.log 可达 50MB）、`is_short_session`、`clear_dir_keep`；抽出 `pack_staging_dirs`（遗留回收与本轮共用）
- `archive_on_startup`：在 rename **之前**判短会话 → `clear_dir_keep(logs, ["watchdog.pid"])` + `clear_dir_keep(devimp, [])` → 置标志 → 遗留 staging 照常回收打包 → `return (None, None)`
- `src/main.rs`：init 后按 `short_session_discarded()` 补打点（归档发生在 init 前，当时无日志可写）
- i18n 新 key `main-log-short-session-discarded`（zh/en 各一条）
- `AGENTS.md`（日志小节新增「短会话丢弃」条，含时区/只读首行/判定次序/watchdog.pid 三条硬约束）、`MEMORY.md`

保守口径：读不到首行、解析失败、时钟回拨（差值为负）都判为「非短会话」走正常归档——绝不因判定失败丢日志；删除时保留 `watchdog.pid`（否则 WebUI 关闭调度失效）。

验证：`cargo +nightly check -p yumi --target aarch64-linux-android` 通过。

需求见上（用户拍板的四条：运行时立即生效 / 改写 meta.yaml / 仅开机清 + 关闭即恢复 / 英文 key + YAML 备份，后缀 .chr）。

### 设计要点

- 三个文件分工：`module/config/rhine-init.yaml`（模式定义，编译期嵌入 + xtask BIN_ONLY 剔除）· `rhine.chr`（模块根，对外暴露，内容 = 模式 key，空/仅注释 = 未启用）· `rhine-back.chr`（daemon 生成的原值快照，还原后删除；**它存在 = 上次启用过实验室**）

- 兜底创建：rhine.chr 缺失补建内置模板（`include_str!("../module/rhine.chr")`），非法覆盖成同一模板 + warn；读不到/解析失败一律按未启用，不因判定失败丢状态

### 设计

- **锁定标记** `chiri-labs.lock` 落在 tmpfs（`LOCK_DIRS = /tmp → /dev` 按序探测可写目录；Android 根目录不一定有 /tmp，/dev 必有。两处都不可写就 warn 一次并放弃锁定，不因为锁失效而让功能不可用）。探测用同目录的 `.chiri-labs.probe` 试写，**绝不碰真实标记**（否则会把已有的锁删掉）。
- **标记格式**：第一行模式名，其后每行 `# 说明`（异常痕迹）。既是 flag（存在即锁定）又是痕迹载体，重启后一起消失——与"建议重启"的处置一致，且不新增对外文件。
- **converge 在锁定期间既不做还原也不接受关闭**：rhine.chr 被清空/改坏一律当关闭请求（写回标记里的模式 + `out.refused` + 留痕 + warn），只做 `reassert`（装回 meta 两个开关与运行时覆盖）；**绝不重写 rhine-back.chr**——此刻 meta 已是改过的值，重写会把改过的值记成原值。快照真丢了才 `write_fallback_backup`（内嵌默认补一份 + 留痕）。
- 锁定期间跳过 restore 很重要：daemon 重启（action.sh / 看门狗）后 rhine.chr 仍是 On，走 restore 会把改动撤掉。
- **告警**：WebUI 读标记 + 三项一致性检查（`data/lab.ts::labWarnings` → 稳定代号 `state-invalid` / `lock-drifted` / `no-backup`）+ 痕迹原文 → 页面顶部 StateBox「检测到运行配置被改动，建议立即重启设备」。锁定中关闭按钮直接禁用 + 提示，`setLabMode(null)` 也兜一层拒绝，不让界面假装成功。

## 审查：复查「锁定 + 告警」这一轮，查出并修掉两个自己引入的缺陷

1. **锁定期间换模式 → 文件与实际状态静默分叉**。`converge` 原写 `lock_mode().or_else(|| state.key())`（标记优先）：手改 rhine.chr 换成别的模式时，key 取的是标记里的旧模式，而 `state` 仍是 `On(..)` → 不触发写回分支 → 直接 `reassert(旧模式)`。结果是 rhine.chr 写着 A、实际跑 B，**两边都没有任何日志**，且不会再被纠正。改为 `state.key().or_else(lock_mode)`（**文件优先**，换模式不拦）+ `else if lock_mode() != key` 把标记首行同步过去（保留痕迹）。关闭请求仍被拦（文件为空/改坏时才走 refused 分支）。
2. **痕迹会写进 i18n 裸 key**。`lock_note(&t("rhine-lock-note-…"))` 若发生在**启动期**收敛（早于 `load_language`），i18n bundle 还是空的、`t()` 原样返回 key，标记里就会出现 `# rhine-lock-note-state-reset` 这种半成品。改用稳定代号 `state-reset` / `close-rejected` / `backup-rebuilt`（`NOTE_*` 常量），WebUI 用 `lab.lock.note.*` 映射成文案、未收录的代号原样显示（LabView 里 `noteText()` 判 `t(key) === key` 兜底）。顺带删掉两个因此变成死 key 的 ftl 条目，`rhine-lock-note-no-backup` 保留但降级为 daemon 日志文案（`write_fallback_backup` 里补 `warn!`，此前只留痕不报）。

复看确认没问题的部分：`reassert` 绝不碰快照；`write_fallback_backup` 只填 def 触及的字段（未触及保持 None = 不变更）；`watch_loop` 在「关闭请求被拒」后会收敛（写回触发的事件里 `next == current` → 不空转，最多 2~3 轮）；`lock_note` 去重 + 上限 8 条；`lock_path()` 探测写 `.chiri-labs.probe` 从不碰真标记。

已知不改（可接受）：① 探测文件删除失败会在 /tmp 或 /dev 残留（tmpfs 重启即清）；② 锁定期间快照被手改坏要等重启走 `restore` 才发现（那时有 warn）；③ `webui/src/data/mode.ts:73` 的类型错是用户 WIP（`CLG_CATALOG` 的 `descKey` 被注释掉但 `describeMode` 仍在用），**不动**。

查出一个真缺陷并修掉：**运行时删除 `down.chr` 不生效**。`utils::DirWatcher` 的掩码硬编码 `CLOSE_WRITE | MOVED_TO`，删文件产生 `IN_DELETE`，watcher 不醒 → 用户删文件（比写空内容更直觉的动作）后调度照旧停摆，直到重启调度（`on_startup` 读到缺失 → 补建 → 不停摆）。修法：`DirWatcher` 新增 `new_with_mask(dir, mask)`（`new()` 委托默认掩码，零行为变化），`down.rs` 用 `CLOSE_WRITE | MOVED_TO | DELETE`。补建的那次写事件不会造成第二轮（prev 已是 false）。

确认没问题的点：停摆启动不会误 init CLG（`get_clg_cfg` 对未知模式返回 `enabled=false` 的默认配置，注释明确写了这条）；不忙循环（5s 自愈只推进计时器 + 事件拦截在 recv 之后）；`kind: 'down'` 在 WebUI 里没有穷举消费方（只有 StateBox 的 kind 无关）；解析口径两端一致（注释、引号、大小写都覆盖）。

已知不修：停摆期间屏幕事件被丢弃 → `is_screen_on` 陈旧；退出后由 app_detect 的双源 verify 在一个周期内自愈。另外停摆只停调度，`rhine_watcher` 仍会按实验室状态改 meta.yaml（两者独立），需要联动再说。

## 追加：导出进度显示（2026-09-17）

用户问能不能显示进度——能，用 tar 自带的 `-v`：

- 脚本：`tar -cvJf "$O.part" -T "$L" >> /dev/chiri_export.progress 2>&1`（逐文件一行），事先 `wc -l < "$L" > /dev/chiri_export.total`；**换回退方案前 `: > "$P"` 清空**，否则三轮行数叠加成 >100%

- 前端：`exportPercent`（done/total，封顶 99，100 留给完成态）+ `exportMb`（`.part` 字节数）；视图加 4px 直角进度条（`--ak-signal-action` 填充）+ 文案「已压缩 X MB · N/M 个文件」，文件数还没算出来时显示「正在准备文件列表」
- 文件少时百分比粒度粗（1 个文件就是 0% → 100%），所以进度文案必须同时给已压缩量，否则看着像卡住
- mock：探测命令回放改成 `s:gz\nb:2097152\nd:1\nt:1\n`
