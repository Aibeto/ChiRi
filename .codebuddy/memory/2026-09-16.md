# 2026-09-16 工作日志

## 核实：FAS 用的是帧间隔还是帧生成时间

结论：**帧间隔**（相邻两次 queueBuffer 的 ktime 差），不是单帧生成耗时。

证据链：

- `yumi-ebpf/src/main.rs` 只有 `handle_frame` 一个 uprobe，挂 `libgui.so` 的 `android::Surface::queueBuffer`，事件体只有 `pid + ktime_ns`（`bpf_ktime_get_ns()`），没有帧开始/结束配对点，原理上也算不出单帧 duration
- `src/monitor/fps_monitor.rs` `ProbeState::ingest`：`delta_ns = ktime_ns - last_ktime_ns`，经 `[1ms, 200ms]` 门后入 `frametimes` 与 `pending`，投喂为 `DaemonEvent::FrameUpdate { frame_delta_ns }`
- `src/scheduler/fas/frame_pipeline.rs` `update_frame`：`actual_ms = delta_ns/1e6`，`current_fps = 1e9/delta_ns`，与 `1000/target_fps` 的 budget 比误差喂 PID/EMA；`heavy_frame_threshold_ms`、`fixed_max_frame_ms` 同口径
- `min_frame_ns() = 1e9 / max_gear() / 2`（`controller.rs`），低于此的间隔直接丢弃

顺带：本轮把超限的 `MEMORY.md` 精简重写（去重合并、移除"旧 WebUI 事实/目标技术栈"等冗余段），并把上述 FAS 口径作为长期事实写入。

## 修复：热重载触发后不生效（WebUI 改 loglevel INFO→DEBUG 无效）

根因在 `utils::watch_path`（已删除，替换为 `utils::DirWatcher`）两处缺陷叠加：

1. **每轮重建 inotify**：`Inotify::init → add_watch → read_events_blocking → 返回即 drop`。两轮之间没有任何 watch 在册，这段窗口内到达的事件被内核直接丢弃。
2. **不过滤文件名**：WebUI 保存是「先写 `meta.yaml.webui.tmp` 再 `mv` 覆盖」（`contract/meta.ts::writeMetaFields`），产生 CLOSE_WRITE(tmp) + MOVED_TO(meta.yaml) 两条事件。监听器被前者唤醒 → 读到**覆盖前**的旧内容（INFO），而真正的 MOVED_TO 恰好落在重载执行期间（旧 fd 已关、新 fd 未建）被丢弃 → 改完永远停在旧值。

对照：`monitor/app_detect.rs::watch_config_file`（rules.yaml）早就做了「常驻 inotify + 按名过滤 + 100ms 静默 + 清空积压」，所以规则热重载没这个问题；meta 这条链路漏了。

改动：

- `src/utils.rs`：新增 `DirWatcher { inotify, buffer }`，`new(dir)` 建实例、`wait_change(file_name)` 只认目标文件的 CLOSE_WRITE/MOVED_TO，其它文件事件忽略继续等；命中后 sleep 100ms 再 `read_events` 清空积压（inotify 0.11 的 fd 默认 NONBLOCK，无事件返回 WouldBlock 退出循环）
- `src/chiri/mod.rs`、`src/scheduler/mod.rs`：两个 config_watcher 改为持有 `Option<DirWatcher>`，实例异常/建失败时置 None 并退避 2s 重建；过滤名取 `config_path.file_name()`
- `src/logger.rs`：`update_level` 加 `LOG_LEVEL: AtomicU8` 记录当前等级，**等级变化时改走 info!**（原来只有 debug!，用户在 INFO 下改完看不到任何回执）——这条是复现/自查的关键
- `AGENTS.md`（热重载断链新增第 4 条）、`MEMORY.md`

验证：`cargo +nightly check -p yumi --target aarch64-linux-android` 通过。

未改动 WebUI——写入链路（单次读改写 + tmp+rename）本身没问题，是监听侧丢事件。

## 修复：特定条件下启动调度不打包 devimp/logs 进 logd

根因：`archive_on_startup` 把 `logs/`/`devimp/` rename 成模块根的 `ziped_<ts>`/`ziped_devimp_<ts>`，再交游离线程 `log_archiver` 异步打包。**进程在打包完成前退出（日志门限 `exit(0)`、panic、手动 kill）会连带杀掉该线程**，staging 目录就此留在模块根——它既不在 `logd/` 也不在 `devimp/`，`enforce_dir_limits` 只扫这两个目录所以扫不到，后续启动也不认领；而 `logs/`/`devimp/` 此时是上一轮重建的空目录，下次启动 `*_has_entries` 为假 → 什么都不归档。现象即「特定条件下启动调度不打包」。触发概率随日志量上升（开 DEBUG/devimp 后 16MB 门限重启变频繁，打包未完就被下一次门限 exit 打断）。

第二个隐患：staging 名用秒级 `MMDD-HHmmss`，同秒两次启动或上一轮遗留同名目录时 rename 报 ENOTEMPTY → `is_ok()` 为假 → **本次整个不归档**。

改动（`src/logger.rs`）：

- 新增 `STAGING_PREFIX = "ziped_"`、`unique_path(dir, stem, ext)`、`unique_staging(root, base)`、`collect_staging_dirs(root)`
- `archive_on_startup`：在 rename **之前**扫描遗留 staging 目录（前置扫描才不会把本轮刚建的目录算成遗留），与本次的一并交同一个 archiver 线程打包，**遗留优先**（本轮若再被打断，下次还能回收）；各自沿用自己目录名生成 zip（保留原时间戳）；空目录直接 `remove_dir_all` 不留空 zip
- 两处 rename 改用 `unique_staging`（`-N` 去重），杜绝 ENOTEMPTY 导致整体不归档
- zip 名不再统一用本次 ts，改为 `zip_name_of(staging_dir)`；返回值语义不变（供 main info 打点）

验证：`cargo +nightly check -p yumi --target aarch64-linux-android` 通过。顺带按 rustfmt 收拢了本轮新增的多行链式调用（`cargo fmt --check` 全仓库本就有大量历史 diff，未整体 fmt）。

未做：未让门限 `exit(0)` 等待 archiver（会拖长重启、有挂住风险），靠下次启动回收兜底已足够。
