# 2026-09-15

## 日志归档改造（logd 被全清修复 + 16MB 打包门限）

用户诉求两条：① 查 `logd/` 可能被全清的问题；② `logs/` 或 `devimp/` 任一文件夹 > 16MB 就立即重启调度以打包日志。

### ① logd 被全清（确认成立，已修）

- 全仓库唯一的 logd 删除方只有 `logger.rs::enforce_logd_devimp_limit`：把 `logd/` 与 `devimp/` 合并成一个 128MB 总预算，按 mtime 跨目录从最旧删到 <96MB。
- 触发条件现实存在：devimp 单文件软上限 128MB、按数量最多留 20 份 → devimp 可涨到约 2.5GB；此时总预算被 devimp 撑爆，而 logd 内的归档包 mtime 恒旧于本会话正在写的 devimp 文件 → 归档包被优先删光（含启动时刚打好的那个）＝「logd/ 被全清」。
- 连带的第二个坑：单文件本身 >96MB 时，「删到低于 target」会把该文件也删掉——单个大归档（旧安装首次归档 logs/ 可达 200MB）会被自己刚打好的 zip 覆盖删除，目录归零。
- 修法（用户选定）：`enforce_dir_limits` → `enforce_dir_limit(dir, max, target)`，`logd/` 与 `devimp/` **各自独立计量**（各 128MB → 各自删到 <96MB），另加「目录内最新的一个文件永不删除」兜底。删掉了 `LOGD_DEVIMP_MAX_BYTES` / `LOGD_DEVIMP_TARGET_BYTES`。

### ② 16MB 打包门限（已实现，事件触发）

- 走「退出进程 + 看门狗拉起」（用户选定）：打包只在启动路径发生，所以重启调度是唯一手段。
- **触发方式按用户要求取开销最低者＝事件触发**（不遍历目录）：daemon 写日志只有三条路径——`daemon.log`（`SelfHealingAppender`）、`status.csv`（`status_write_line`）、`devimp`（`devimp_write_line`），三条落盘后各调一次 `logger::note_write(&LOGS_BYTES_WRITTEN|&DEVIMP_BYTES_WRITTEN, "logs/"|"devimp/", n)` 记账；`logs/` 或 `devimp/` 本会话累计写入任一 ≥ `LOG_RESTART_THRESHOLD_BYTES`（16MB）即 `std::process::exit(0)`，看门狗 3s 后拉起、新进程在 `logger::init` 前把两目录打包进 `logd/`。零额外 syscall（不再有 5s/60s 巡检）。
- 累计写入量≈目录实际大小：轮转/清理前（daemon.log 50MB、status.csv 8MB+备份、devimp 单文件 128MB）不会删任何已计字节；每进程从 0 计起（启动归档已清空两目录）。
- 安全阀：无看门狗（`watchdog_pid()` 为 None，调试直跑/孤儿态）**不退出**且计数清零（避免每行写都读 /proc）；退出前打点的日志本身也走同一写路径，用 `LOG_RESTARTING` 原子标志防重入。
- 生效范围：`note_write` 首行 `is_chiri_soc()` 门控——只有 Chiri SoC 生效（Yumi 侧调度逻辑冻结），代码虽在共享的 logger.rs 中但不会影响 Yumi。
- 新增 i18n key `logger-log-restart-for-archive`（zh/en 各一条）。
- 中途被推翻的两版：① 「chiri 5s 周期块巡检两目录大小」；② 该版上加的 60s 最小运行时长死循环保护（事件触发后每轮重启需重新写满 16MB，结构上不会死循环，一并删除）。

### ③ 看门狗重启能力核查（用户提问）与补强

核查结论：**进程级终止能重启，线程级死亡不能**（看门狗只看进程存活）。

- 成立：循环前台跑 daemon（不 fork，只有 setsid + PDEATHSIG=0）→ 进程一结束就重启；main panic → 退出 101；monitor_core panic → `main join().unwrap()` 带进 main → 退出；chiri 调度线程连续 panic >5 次 → `exit(1)`；日志门限 `exit(0)`。
- 缺口（本次修 1、3；用户明确 yumi 视为废弃、手动关闭/重启属设计功能，故 2、4 不修）：
  - ① 监控子线程（screen/config/pid/fps/cpu/telemetry）是游离线程，panic 只死线程、进程照活 → 看门狗感知不到、监控永久缺失。**修法**：`monitor/mod.rs` 新增 `spawn_guarded(name, f)`（catch_unwind→Err 时纯英文 `log::error!` 后 `exit(1)`），6 处 `thread::Builder::spawn` 全部改为它；正常返回不受影响。
  - ③ 看门狗固定 `sleep 3`，启动即崩会形成重启风暴。**修法**：`service.sh`/`action.sh` 循环内用 `date +%s` 量存活时长，<60s 则 sleep 3→10→30→60s 递增封顶（`case` 实现），活过 60s 或 date 不可用时回到 3s。
- 仍未覆盖：daemon 硬挂（死锁/死循环）——看门狗无存活超时探测；用户选择只加退避，未做（需 daemon 后台运行 + stat current_mode.chr 的监控循环）。
- 验证：`cargo clean -p yumi` + check 通过、无告警；`cargo fmt --check` 对本次触及文件（logger/main/monitor/chiri）无 diff。**shell 未能本地校验**（本机 bash 走 WSL 无发行版），两个 sh 的改动仅人工复核。
- 文档同步补强：`AGENTS.md` 看门狗条改写（触发链路清单 + spawn_guarded + 崩溃退避）；`MEMORY.md` 新增看门狗核查条目。

### ④ 未提交代码审查（同日）
