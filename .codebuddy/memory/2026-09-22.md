## 二十四轮：8550 + 8745 双机型日志分析（性能/流畅度/功耗平衡）

产物 `.codebuddy/docs/2026-09-22-8550-8745-power-balance.md`（只分析未改码）。

**数据筛选（关键，别混着用）**：
- 8550：72 个 devimp 文件**全是 A04-Canary88、全是 40 列** → devimp 48 列（CPU/GPU 实际频率）**这次没刷入**，
  本次只能看调度器写入的决策值。
- 8745：33 个文件**三个版本混着**（A02×2 / A03×10 / A04×21）。**A03、A02 的功耗列是坏的**：
  `batt_i` 出现 −369 / 656 A、`batt_p` 达 245 万 W（单位/口径错误）→ 这两版本的功耗不可用，
  但频率/util/tgtop 仍可参考。A04 正常（与 8550 同版本）。

  （QQ 1657/2175、trim 562/1213、bili 625/1885）→ 不滤会把 39W 快充算进功耗
  （QQ 6.85W→3.03W、trim 14.31W→1.85W）。status.csv 有 charge 列但样本很少（8550 仅 35 行放电）。

**9-20 视频调参效果已验证（同口径滤充电）**：batt_p **2.83 → 2.08 W（−26.5%）**、p50 2.59→1.77、
batt_temp −2.0℃、cpu_temp −5.9℃、**不再触发 70% 限频**（cap 87→100）、
little cap p95 100→66.7、prime p95 83.8→46.1，而 **util 三簇几乎不变**（0.63/0.50/0.27 → 0.60/0.49/0.26）。
→ 省的是「频率高于负载所需」的部分；「压天花板 + 收紧 headroom + 滤尖峰」这条路可推广。

**剩余空间（按量级）**：
1. **日常 default（CLG）头号**：util 仅 0.5 左右，但 cap p95 **全是 100%**（launcher/tongyi/emmx/QQ 皆然）
   → 根因是 `default.cpu_load_governor.perf_ceil = 1.0`（无天花板）。功耗 launcher 2.08W、tongyi 2.28W、QQ 3.03W。
2. **8745 游戏（明日方舟 akmode）7.06W**：big cap p50 **100%**、util 0.72、gpu 74.1%；
   akmode 是 headroom 1.15 + util_smoothing 1.0 + **无 perf_ceil** → 尖峰直接顶满。
3. **8550 游戏（sgame fas）3.94W 且 cap 70%**：batt_temp 40.7 顶到 soft 41 → 陡峭 70% 限频（掉帧风险）。
4. **8745 待机 0.38W 已极低**，但 little util 0.71（cap 仅 22%）→ tgtop 显示 **logd 占 17.44%**（待机头号）。

**采集态开销警示**：logd 待机 17.44%、launcher 15.82%、游戏 9%；8745 待机 5h 产出 **16.7MB** devimp（≈0.9KB/s）。
日志里的功耗/负载**包含采集自身开销**——评估任何改动必须前后都在同一 dev_record 状态下比。

**方案**：P1 日常 CLG `perf_ceil 1.0→0.80` + `touch_boost_ms 350→400`（稳态降频、交互靠 boost 兜，别只降 ceil）；
P2 CLG 补 per_cluster（tuned 9-21 已有，CLG 只有全局一份）；P3 akmode 加 `perf_ceil 0.95` +
`util_smoothing 0.85`；P4 8550 游戏把陡峭 70% 改平缓（soft_cap 0.70→0.85，别动安全阈值本身）；
P5 采集开销：tgtop 30s→60s 可配（snap 1s 保留）；P6 devimp 补 `charge` 列 + 刷入 48 列版本。

fps 列全为 `-`（FAS 未采样），流畅度只能靠 cap% 与主观间接判断——后续若要量化需先让 FAS 采样可用。

## 二十六轮：Canary90 首批日志验证 —— P1/P2/P4 生效，但功耗涨 47%（采集的锅）

产物 `.codebuddy/docs/2026-09-22-canary90-verify.md`。样本 `devimpbin/8550/logd_0922-020050.tar.gz`
（0922-00:52~02:00，52 文件、**48 列**、Alpha04-**Canary90**；上一批是 40 列 Canary88）。

**参数生效（好消息）**：日常 default 的 cap p95 从 100/100/100 → **72.4 / 82.9 / 69.9**，
与配置 little 0.70 / big 0.80 / prime 0.65 精确对应 → **per_cluster 确实按簇生效**。
游戏 fas 的 cap 从 70 → **85**（P4 的 soft_perf_cap 0.85 ✓），该场景 governor=performance 且 cur=min=max（FAS 锁频）。

**功耗全面上升（坏消息）**：
- 同活跃度（亮屏+放电，按 gpu 档）：gpu<10 档 1.86→**3.17W（+70%）**、cpuT 47.5→58.7℃。
- 同场景 B站 playback（gpu<12）：9-20 基线 2.39W → 00:14(C88) **1.76W** → 02:00(C90) **2.59W（+47%）**。
- **判据**：C90 与 C88 的 playback 频率上限完全一致（little/big p95 = 66.7/75.9），即该场景调参没动过，
  功耗却涨 47%，且 util（0.60→0.66）、psi（18.6→23.2）、cpuT（+6.9℃）同步涨 → **涨的是 C90 新加的东西**。

**根因**：C90 新增的 devimp 48 列采集里，**每秒读 GPU 频率节点 = 每秒把 GPU 从低功耗唤醒一次**
（读 Adreno gpuclk / devfreq cur_freq 需要 GPU 供电应答；表现为 gpu_busy 仅 5.2% 但功耗温度都涨）。
CPU 的 cpufreq 节点读取则廉价、无此副作用。devimp 既有设计里 place/core 8s、tgtop 30s，只有 snap 是 1s，
把「读 GPU 硬件状态」挂在 1s 上是这轮的设计失误。

**修复（已做，cargo check 通过）**：
1. `src/chiri/mod.rs` 新增 `gpu_snapshot_due()`：**GPU 快照节流到 10s**（未到点 4 列写 `-`），CPU 仍每秒采。
2. `src/chiri/gpu.rs` 修 48 列 GPU 数据的三个 bug：**单位**（cur_freq/gpuclk 是 Hz → 换算 kHz，
   原来写出 110352386 这种 110GHz 值）、**目录去重**（kgsl-3d0 同时存在于 devfreq 与 kgsl 两个路径，
   混读导致 min 680MHz 配 cur 110MHz，改为按设备名去重、devfreq 优先）、
   **governor**（只在标准 devfreq 读，Adreno 私有目录同名节点是频率值；纯数字判无效写 `-`）。

**待用户确认**：Canary90 除了这批改动是否还有别的（若有也要纳入嫌疑）；
刷修复版后复测 playback 是否回落到 ~1.76W（回落即确认是 GPU 采集的锅，P1~P4 收益可保留；不回落则二分排查）。

## 二十八轮：审查 DOWN 模式（调度停摆）是否实际可用

**机制**（`src/down.rs`）：模块根 `down.chr` 写保留字 `down` → 停摆；与 rhine.chr 同款、落盘持久化（重启仍停摆）。
`on_startup` 读一次 → `DOWN_ACTIVE` 原子量；`watch_loop` 用 inotify（CLOSE_WRITE|MOVED_TO|DELETE）盯文件。

**代码审查结论：实现完整**（`chiri/mod.rs` 1046-1101 状态机）：
- 进入停摆 release 清单：CLG、ak_governor(tuned)、fast_lock、FAS、affinity、lab_static、
  governor_guard、gpu_guard、core_ctl、`CpuScheduler::restore_system_tweaks()`（一次性调整还原），
  顺序是「先交回系统再写状态文件」。
- 退出停摆按 **monitor 实时模式**重建（非停摆前快照），并显式重建 fas/特调（事件不会补发）。
- 启动即停摆：`on_startup` 前置 + `down-boot-halted` 日志（否则与「调度线程没起来」同形）。
- 停摆期事件照收但不下发，仅吸收 `ScreenStateChange`；60s 一条心跳（区分「停摆生效」与「进程死了」）。
- `module/down.chr` 模板已随模块下发，写法清楚。

**实测证据：无**。三批日志（8550 00:14 / 8550b 02:00 / 8745）的 daemon.log **无任何 down 字样**，
devimp 的 mode 列只有 default/fas/playback → **DOWN 从未被触发过**，运行时可用性无证据。

**三条审查提醒（非 bug，是要知道的取舍）**：
1. **停摆期 eBPF 探针仍挂载**（采集照常）：`sched_switch` 每次上下文切换都跑 → 基线不是「完全干净的系统」。
2. **停摆期 devimp/status.csv/daemon.log 照常写** → 结合上次「logd 待机占 17%」的教训，
   **停摆期采集到的功耗基线包含采集自身开销**，做 A/B 时要知道这个偏差（或停摆期同时关 devimp）。
3. 启动时 `GpuGuard::new()` 仍会给 GPU 节点 chmod 0664（只改权限不改值，此前已确认可接受）。

## 二十九轮：完成 frozen 模式（待春归 / 春风来）

以 vector 为模板、方向相反：**锁硬件最低频**（vector 锁最高）+ 停掉一切额外开销。
界面显示名「待春归」、描述「春风来」（en: Waiting for Spring / The spring breeze comes）。

**核心代码**：
- `src/chiri/fast.rs`：`init(lock_min: bool)`；`LockedPolicy` 加 `target`（hw_min 或 hw_max）；
  **写序是坑**——升频「先 max 后 min」、降频「先 min 后 max」，否则出现 min>max 被内核拒绝；
  tick 重写用 `target` 而非 `hw_max`。
- `src/chiri/mod.rs`：新增 `is_fast_lock(mode)`（vector|frozen），**六个入口统一**（启动 / 亮屏恢复 /
  ModeChange / ConfigReload / DOWN 退出 / panic 自愈，含 `apply_mode_takeover`），每处 `init(mode=="frozen")`。
- **停开销**：`logger.rs` 两道闸——`devimp_active()` 按 `DEVIMP_MODE=="frozen"` 返回 false、
  `status_log_snapshot()` 开头 `mode=="frozen"` 即 return（**保留 daemon.log 便于排错**）；
  线程亲和/绑核与 core_ctl 由 rhine 的 `thread_bind: false` 交还系统（`config.rs:1124-1125`
  把 `affinity.enabled`/`core_ctl.enabled` 与 meta.thread_bind 取与，自动生效，无需改代码）。
- `src/notify.rs`：`frozen` 归入 RHINE 家族。

**配置与前端**：`rhine-init.yaml` 的 frozen 从 `{}` 改为 global_mode/fas/scenemode/special_tuned/**thread_bind=false**；
`webui/src/data/lab.ts`（`LAB_ENABLEABLE` 加 frozen、`LAB_TAKEOVER.frozen` 加 `thread_bind`）、
`mode.ts`（LAB_CATALOG 加 frozen，signal 用中性 info——它不是危险档）、zh/en i18n、`lab.test.ts`
（原断言「frozen 保持预留 not.toContain」已改为「都给启用入口」）；
`module/rhine.chr`、`docs/agents/03-chiri.md` 同步。

**验证**：`cargo check`（android）通过；`npx vitest run` **85 passed**。
**未停的开销**：eBPF 探针仍挂载（sched_switch 等），用户态不再落盘但内核侧观测开销还在——
若要「完全干净」的基线需另做探针摘除（即报告里的 K3）。

## 三十轮：审查 frozen 改动（发现 1 个真 bug + 修了 3 处）

**真 bug（必现）**：`mod.rs` 的 ConfigReload 分支里有一处 `current_mode == "vector"` 没纳入 frozen
（2597 行附近）。frozen 落到下面的 `else if current_mode != "fas"` 会执行 **`fast_lock.release()`** ——
配置热重载（改 meta/rules 即触发）时把刚锁上的最低频又放掉，frozen 静默失效。
已改 `is_fast_lock(&current_mode)`；同文件另一处同类分支（1247）一并统一。
**校验手段**：`git grep -n '== "vector"' src` 结果应为空（现已为空，只剩注释与配置段名）。

**另两处修正**：
1. `logger.rs::devimp_active()` 原来用 `DEVIMP_MODE.lock()` 判 frozen —— 该函数是每条 devimp 行
   写入前的闸门（特调下 25 行/s/组），高频路径不该加锁。改为 `DEVIMP_FROZEN: AtomicBool`，
   由低频的 `set_devimp_mode()` 维护（与项目「高频只读原子量」的口径一致）。
2. `mod.rs::apply_mode_takeover` 里 `mode == "vector" || mode == "frozen"` 字面量 → 改用 `is_fast_lock(mode)`。

**确认无问题**：`fast.rs` 的 target/写序（升频先 max 后 min、降频先 min 后 max）；
contingency 的 `init(false)` 正确（它锁最高频）；frozen 不进 `is_boost_mode`、走
`sync_lab_governor_gpu` 的 `_` 分支（不锁 GPU）；亲和与 core_ctl 由 `thread_bind=false` 关闭。
cargo check 通过。**遗留风险（未改，需知悉）**：锁最低频后设备极慢、解除靠改 rhine.chr + 重启
（建议 adb 操作）；status.csv 停写后 WebUI 实时数据不更新（预期）；eBPF 探针仍挂载（内核侧开销）。

## 三十三轮：PowerBase 逻辑审查 —— 修掉一个「静默永久失效」的真 bug

1. **★ 致命：接管时不写频率，会导致首次降频永久写失败**。原实现 init 只把内部 `perf` 置 0、**不动硬件**，
   于是首个 tick 判「升频写序」（perf 0 < target）→ 先写 max（低位），而 min 还是接管前的值
   （可能是 800MHz）→ **max < min 被内核拒绝** → 写失败 → `perf` 不前移 → 下一 tick 重试同样失败 →
   **PowerBase 完全不生效，且一行错误都不会打**。
   修：init 时**立刻把 min=max 写为硬件最高频**并把 `perf` 同步为 1.0（写成功才置 1.0，失败保持 0.0
   走升频写序重试）。取最高频起手而不是最低：接管瞬间通常有负载，先给余量防掉帧，
   紧随的 tick 会按功耗规则迅速压下来。
2. **振荡缺陷：`target *= down_scale` 一步砍半**。频率骤降 → 下一 tick 因利用率反馈滞后把 util 顶回去
   → 升回 → 再砍，来回振荡且平均功耗更高。修：在 `down_scale` 之上加单次降幅上限
   `MAX_DOWN_STEP = 0.25`（降频仍即时、不看功耗，但不会一步到底）。
3. **写入死区 0.01 → 0.05**（`PERF_DEADBAND`）：抑制抖动，并把 sysfs 写入从「每 tick 可能有」降到
   「只在真正变化时」。
4. 顺带修编译错误：`max_writer/min_writer` 必须 `mut`（`write_value_force` 取 `&mut self`）。

`cargo check` 通过。**仍未接线**（开关保持默认 false；接线前开开关会「CLG 释放、PowerBase 未接管」）。

**PowerBase 剩余问题清单（用户问「还有什么问题」时梳理，按阻塞度排）**：

  功耗要从 scheduler_ipc 的 `power_now` 取（并判断放电）、触摸状态 CLG 那份是私有的需另备共享标志。
