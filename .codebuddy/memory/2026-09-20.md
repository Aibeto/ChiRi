# 2026-09-20

## 一轮：修复「启用 DOWN 模式后调度仍在运行」

**根因**：DOWN 的释放清单覆盖不到「写 sysfs 但不属于任何 governor」的那类调用面——
`chiri::scheduler::CpuScheduler::apply_system_tweaks`（cpuidle governor、IO 调度器/预读/合并、
屏蔽 cpu_boost 输入升频，以及本轮 WIP 新加的内核 Sched 段 sched_migration_cost_ns /
sched_nr_migrate）此前完全无停摆感知：启动时先于 DOWN 判定下发，之后每次 meta 热重载由
config_watcher 线程无条件重放。直接后果就是「开了 DOWN，调度仍在被改」——它们不在任何
governor 的快照链里，`release()` 清单碰不到，停摆期残留整段。

**改法**（三层）：
1. `src/chiri/scheduler.rs` 加 `[snapshot]`：静态 OnceLock<Mutex<HashMap<路径, 原值>>>，首次写某
   节点前记录原值（重复下发不覆盖，否则把上一次 tweak 的值当成系统原值）；IO 的 queue/scheduler
   读出来是候选列表、当前值带方括号，写回前必须剥壳。新增 `restore_system_tweaks()`（drain 快照
   逐个写回 + 计数日志，快照空则 no-op）。四个下发点改走 snapshot_write / snapshot_nodes。
2. `src/chiri/mod.rs`：DOWN 进入分支调 restore_system_tweaks；退出分支在重接管后补发一次 tweaks
   （为此 clone 了 tweaks_sys_path）；启动下发与 config_watcher 下发加 `crate::down::is_down()`
   门控（那条线程拿不到循环内的 halted，只能读进程级原子标志）；down_watcher + on_startup 上移到
   首次 tweaks 之前（否则「重启后仍停摆」的那次启动会先写一遍）。
3. 循环内三处隐式门控改显式：fas_mgr.tick()、1s 的 fas 兜底/自愈块、触摸事件消费、fast_lock.tick()
   （改为 halted 时返回 None），以及 panic 自愈后的「按当前模式重接管」块——原只靠 mode 恰为 down
   才安全（get_clg_cfg 对未知模式 enabled=false），模式停在 vector/lab 就会把刚释放的接管重建回来。

**i18n**：新增 system-tweaks-restore（带 count 参数）与 system-tweaks-skipped-down，zh/en 同步。

**验证**：`cargo check -p chiri --target aarch64-linux-android` 通过（Windows 本机不能跑 default
target：netlink-sys / aya-obj 报 libc 缺符号，属既有环境限制，检查必须带 --target）。WebUI 未改动、
未跑 vitest。机上行为未实测。

## 二轮：未提交改动全量审查（含自查）

## 五轮：DOWN「仍未解决」——启动块残留写入

用 code-explorer 全仓审计「停摆期仍写 /sys·/proc 的调用点」，结论：**循环内已无残留**
（周期块全部 `!halted`、事件在 `match` 前 continue、monitor/rhine 各线程零 sysfs 写），
问题全在**进入循环之前的启动块**：

1. `corectl_mgr.force_online_all()` → 写 `cpuN/online=1`（为 CLG/fast_lock 初始化铺路，
   而停摆时它们根本不初始化）→ 加 `!halted` 门控。
2. `GovernorGuard::cleanup_residue()` → 见到 `performance` 就写回 schedutil，**这正是用户
   日志里那三行 WARN：停摆期 ChiRi 仍在写调度节点**。改：停摆期走新增的
   `report_residue()` 只报不写（`governor-residue-down`，zh/en 同步），理由——「上一轮
   ChiRi 的残留」与「厂商/内核默认就是 performance」进程无从区分，写了就把基线改成
   ChiRi 认为的样子。为此在 `governor.rs` 抽出 `each_residue_policy()` 供两条路径共用。

**已知边界（写进 02-convention）**：所有 release/restore 都依赖**进程内**快照，只重启
daemon（不重启设备）时上一轮写过的 `scaling_max_freq`/governor/cpuset/uclamp/core_ctl/
一次性 tweaks 本进程无从还原——干净基线必须重启设备（或后续做快照持久化）。
另：非 ChiRi SoC 分支（`src/scheduler/`，Yumi）**完全没有 DOWN 支持**（`on_startup`/
`down_watcher` 只在 chiri 分支起），待用户定是否要接。`cargo check` 通过。

## 六轮：用户贴新日志——daemon 层已证明生效，剩下的多半是「手动重启」残留

新日志（16:24）已带 `down-boot-halted`，说明新二进制装上了；且**三行
`检测到残留 performance…已恢复 schedutil` 消失**（上一轮改成停摆期只报不写后，本次
也没有 policy 处于 performance）。逐条证据表明 daemon 层 DOWN 已生效：tweaks 跳过、
无 `scheduler-clg-init`、无亲和/core_ctl 接管、无 governor 写入；app_detect 那条
`模式变更 -> default` 是 monitor 线程自己的判定（照常跑），调度循环在 `match` 前就
continue，之后本就不该再有调度日志。

关键线索：日志首行「上一轮会话存活不足 30 秒」= 用户是**手动重启调度（Action）**而不是
重启设备 → 上一轮 ChiRi 写过的 sysfs（`scaling_max_freq`/governor/cpuset/uclamp/core_ctl/
一次性 tweaks）全部残留在系统里，新进程快照为空、停摆也不还原 → 用户看到的系统仍是
「被 ChiRi 改过的」，这就是「DOWN 看起来不生效」最可能的原因。**口径：要干净基线必须
重启设备。**

改动：心跳 300s → **60s** 并带上已持续分钟数（`halt_since`，启动即停摆时取 now、进入
停摆时置位、退出时清空；`down-heartbeat` 加 `{ $mins }`，zh/en 同步）——停摆期日志完全
静止，用户只能靠这一行区分「停摆中」与「进程已死」，间隔太长等于没有。`cargo check` 通过。
已请用户回贴：`current_mode.chr`、`policy*/scaling_governor|scaling_max_freq|cpuinfo_max_freq`、
`status.csv` 末行、`down.chr` 的实际值，用于定位到底还有谁在改系统。

## 七轮：用户口径澄清——「只要 ChiRi 停止调整，其他调度会立即接管」

→ 之前那条「要干净基线必须重启设备」对用户场景**不必要**（那只影响基线纯净度，不影响
另一个调度接管：它会自己覆盖 ChiRi 的残留值）。据此把停摆期最后几处**启动期**干预全部
显式门控（不再依赖「内存模式恰好是 down」这个脆弱不变量）：
1. `corectl_mgr.force_online_all()`（写 `cpuN/online=1`）→ `!halted`（六轮已做）；
2. `GovernorGuard::cleanup_residue()` → 停摆走 `report_residue()` 只报不写（五轮已做）；
3. **本轮新增**：启动接管 `fast_lock.init()` / `cpu_governor.init_policies()` 包进
   `if !halted`——原来靠 `current_mode=="down"` 时 `!= "vector"` 且 `get_clg_cfg("down")
   .enabled==false` 间接跳过，feature.yaml 里若出现名为 `down` 的模式段就会在停摆期开机
   直接锁频/接管 CLG。
**停摆期 ChiRi 唯一还会动系统的动作**：启动时 `GpuGuard::new()` → `FastWriter::new` →
`utils::enable_perm` 给 GPU 频率节点 chmod 0664（只改权限不改值，且放开权限不阻碍其他
调度；退出停摆后仍需该对象，故未门控——已向用户说明）。`cargo check` 通过。
