# 2026-09-20

## 一轮：修复「启用 DOWN 模式后调度仍在运行」

**根因**：DOWN 的释放清单覆盖不到「写 sysfs 但不属于任何 governor」的那类调用面——
`chiri::scheduler::CpuScheduler::apply_system_tweaks`（cpuidle governor、IO 调度器/预读/合并、
屏蔽 cpu_boost 输入升频，以及本轮 WIP 新加的内核 Sched 段 sched_migration_cost_ns /
sched_nr_migrate）此前完全无停摆感知：启动时先于 DOWN 判定下发，之后每次 meta 热重载由
config_watcher 线程无条件重放。直接后果就是「开了 DOWN，调度仍在被改」——它们不在任何
governor 的快照链里，`release()` 清单碰不到，停摆期残留整段。

**改法**（三层）：
1. `src/chiri/scheduler.rs` 加 `[snapshot]`：静态 OnceLock<Mutex<HashMap<路径, 原值>>>，首次写某
   节点前记录原值（重复下发不覆盖，否则把上一次 tweak 的值当成系统原值）；IO 的 queue/scheduler
   读出来是候选列表、当前值带方括号，写回前必须剥壳。新增 `restore_system_tweaks()`（drain 快照
   逐个写回 + 计数日志，快照空则 no-op）。四个下发点改走 snapshot_write / snapshot_nodes。
2. `src/chiri/mod.rs`：DOWN 进入分支调 restore_system_tweaks；退出分支在重接管后补发一次 tweaks
   （为此 clone 了 tweaks_sys_path）；启动下发与 config_watcher 下发加 `crate::down::is_down()`
   门控（那条线程拿不到循环内的 halted，只能读进程级原子标志）；down_watcher + on_startup 上移到
   首次 tweaks 之前（否则「重启后仍停摆」的那次启动会先写一遍）。
3. 循环内三处隐式门控改显式：fas_mgr.tick()、1s 的 fas 兜底/自愈块、触摸事件消费、fast_lock.tick()
   （改为 halted 时返回 None），以及 panic 自愈后的「按当前模式重接管」块——原只靠 mode 恰为 down
   才安全（get_clg_cfg 对未知模式 enabled=false），模式停在 vector/lab 就会把刚释放的接管重建回来。

**i18n**：新增 system-tweaks-restore（带 count 参数）与 system-tweaks-skipped-down，zh/en 同步。

**验证**：`cargo check -p chiri --target aarch64-linux-android` 通过（Windows 本机不能跑 default
target：netlink-sys / aya-obj 报 libc 缺符号，属既有环境限制，检查必须带 --target）。WebUI 未改动、
未跑 vitest。机上行为未实测。

## 二轮：未提交改动全量审查（含自查）

**自查出的缺陷并已修**：停摆判定与下发跨两个线程（`config_watcher` 与调度循环），存在
「判完 `is_down()` 后被另一线程切进 DOWN」的窗口 → tweak 会写进停摆期。修法：把判定下沉到
唯一入口 `CpuScheduler::apply_system_tweaks`，新增静态互斥闸 `tweaks_gate()`，apply 与
`restore_system_tweaks` 都在闸内复查停摆标志；mod.rs 两处调用点去掉门外重复判定。

## 四轮：安装期电池校准 + DOWN 可观测性

**A. `module/customize.sh` `[oplus-detect]` → `[battery-detect]` 重写**
- 定位 meta 抽成 `locate_meta_file()`（active_config.chr → ro.soc.model → 放弃），sed 提为全局 `SED_CMD`；
  主入口 `apply_battery_defaults()` 先定位 + 取 sed，再二选一：私有节点可用 → `apply_oplus_switches()`，
  否则 → `apply_standard_divisor()`。改的是 `$MODPATH`（modules_update 暂存）里当前机型那份
  meta.yaml：完整安装由安装器落地、热更新由 `cp -r` 覆盖，两条路同源（用户明确要求两条路都要做）。
- 标准节点校准：读 `/sys/class/power_supply/battery/voltage_now`，n 位 → 除数 = 1 后跟 n-1 个 0
  （4382→1000、4382000→1000000），`voltage_divisor` 与 `current_divisor` 同值；首位非 3/4、
  非纯数字或节点不可用就不写（宁留默认让用户在 WebUI 改）。daemon 运行期仍不猜量级，只有安装器
  装机那一刻按节点量级写一次——与「去除内置启发式」的口径不冲突。
- 修双电芯误判：原 `cut -d',' -f 12` 判非空，字段不足 12 个时 cut 把整行透传 → 单电芯机型被判成
  双电芯；改为先数逗号确认 ≥12 字段、第 12 个字段为正数（与 `read_oplus_bcc` 同口径）。
- 热更新末尾「恢复备份」改为只在保留配置那条路执行：选了覆盖却把旧 `config/meta.yaml` /
  `rules.yaml` 盖回去会顶掉刚写入的校准（回退机型生效配置就是根上那份），而 ChiRi 机型的生效配置
  `config/<soc>/meta.yaml` 本就不在这条备份链里，行为本就不一致。
- 双语文案新增 MSG_VOLT_CHECK/APPLY/FAIL，并修正 MSG_OPLUS_NO_SED 的 zh 文案（原写成「检测为非
  oplus 机型」）、两条 NO_META/NO_SED 文案补上「校准倍数」。

**B. DOWN「疑似未生效」核查结论**：用户贴的日志里 `[Tweaks] DOWN 停摆期间跳过一次性系统调整下发`
证明 DOWN 在调度线程启动**之前**就已识别（on_startup + down_watcher 排在首次 tweaks 之前），
「调度先于 DOWN 识别」的假设不成立；日志之后空白是因为停摆中周期块大多被 `!halted` 门控、
事件在 `match` 前 continue，而**开机即停摆时状态机不走「进入停摆」分支**（`halted` 初值 =
`is_down()`），于是全程零停摆字样，与「线程没起来」同形。改法：`src/chiri/mod.rs` 启动即停摆打
`down-boot-halted`（warn），并新增 `DOWN_HEARTBEAT_INTERVAL`(300s) 心跳 `down-heartbeat`（info）。
i18n zh/en 同步两个键。`cargo check -p chiri --target aarch64-linux-android` 通过。机上行为未实测。
